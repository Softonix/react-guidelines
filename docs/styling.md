# Styling

How styling is approached across the codebase. The underlying setup (theme block, Mantine overrides, CSS-module conventions) lives in `app-setup.md`; this doc covers the philosophy and the rules.

The design system is a **contract**. Every value should have a token. If a token doesn't exist, add it before writing the code that needs it. "Just this once" is how systems decay — inline values rarely get promoted to tokens later.

---

## Tokens are the contract

**Hard rules:**

1. No hex literals, no `rgb()`/`rgba()`, no named colors in `app/views/`, `app/widgets/`, `app/features/`, or `app/entities/`. Raw color values are only allowed in the theme source — the Mantine palette (`app/shared/mantine/colors.ts`); the autogenerated `app/theme.css` is rebuilt from there.
2. No static values in `style={{}}`. Inline `style` is reserved for **genuinely-dynamic** values — animation-delay computed per row, gradient stops driven by React state, off-canvas decorative gradients that don't fit a Tailwind utility. If the value is static, it doesn't go in `style`.
3. No raw Mantine palette references like `color="blue.6"`, `c="gray.7"`. Use the project's semantic palette names or the semantic Mantine var the resolver wires up (e.g. `c="dimmed"`).
4. No reaching for `Stack`, `Group`, `Box`, `Flex` from Mantine. Tailwind covers it with less indirection. Mantine layout primitives are reserved for cases where they pull theme tokens you'd otherwise have to wire by hand (rare).

If you need a value that doesn't exist, **add a token** — to the Mantine theme (`app/shared/mantine/`) for design-system values that flow into `app/theme.css`, to `@theme inline` in `app/app.css` for Tailwind-only utilities, and (if Mantine needs a non-palette CSS var) to a `cssVariablesResolver` wired into `MantineConfigProvider`.

---

## The three tools

Pick the one closest to the concern. Don't mix all three on a single element.

| Tool | Use for |
|---|---|
| **Tailwind utilities** | Layout (flex, grid, spacing, sizing), positioning, colors via tokens, typography weight/tracking, one-off arbitrary values |
| **Mantine props/theme** | Component-internal styling — `size`, `radius`, `color`, `variant`, `c`, `fw` |
| **CSS modules** | Project-wide Mantine overrides via `classNames` only — never page-level styling |

`motion` is the fourth concern — see § Motion. It is **not** a styling tool; it animates between styled states.

---

## Color

Color tokens are defined as CSS variables and exposed as Tailwind utilities + Mantine theme entries. Never reference a hex literal in a consumer slice — always go through the named token.

Group your tokens semantically rather than by raw shade. Typical groups:

- **Surfaces** — page background, cards/wells, inputs/popovers, overlays.
- **Text (ink)** — primary, soft, faint, muted, on-accent.
- **Borders (rules)** — default, strong, faint.
- **Accent(s)** — primary brand color, secondary accent. Pair each fill token with a matching text token tuned for inline use on the canvas (different contrast needs).
- **Semantic feedback** — danger, success, info.

For Mantine `<Text>`, prefer the semantic variant (`c="dimmed"`) over palette references.

---

## Typography

Use **one font family**. Differentiate by **weight and tracking**, not family. Headings via Mantine `<Title order={1..6}>`; body via `<Text size="sm|md|lg">`; raw labels/eyebrows/captions via `<p>` / `<span>` with Tailwind utilities.

A coherent type scale defines weights and tracking per level (display, headings, body, helper, eyebrow, tabular). Promote a step to a token rather than re-inventing it in every consumer.

---

## Spacing & layout

Prefer **generous spacing**. Restraint with copy density, generosity with breathing room. The Tailwind spacing scale is tied to `--mantine-scale` so Tailwind and Mantine agree. Don't reach for arbitrary spacing (`p-[14px]`) without checking the scale — there's almost always a token close enough.

### Breakpoints

Tailwind and Mantine share one set of breakpoints. `app/theme.css` exposes Mantine's scale as Tailwind's `--breakpoint-*` tokens (`xs: 36em`, `sm: 40em`, `md: 48em`, `lg: 64em`, `xl: 80em`), and `shared/mantine/index.ts` sets the matching values on the Mantine theme. Mobile-first: write base utilities for mobile, layer `sm:` / `md:` / `lg:` for larger viewports.

## Forms

Always Mantine components — never raw `<input>` / `<textarea>` / `<button>` (except honeypots and similar intentionally-hidden inputs).

- **`TextInput` / `Textarea`** — `{...form.getInputProps('field')}`, `error={fieldError('field')}`. Themed defaults handle radius/size/variant. Label rendering and focus ring come from per-component CSS modules — don't override at the call site.
- **`SegmentedControl`** — for binary or 3-way choices. `fullWidth` on mobile.
- **`Radio.Group` + `Radio`** — for >3 options where SegmentedControl would crowd. Wrap items in `flex flex-wrap gap-x-8 gap-y-3`.
- **`Select` / `MultiSelect`** — for long lists. Always pass `searchable` if >7 options.
- **`Button`** — `loading={isPending}` for async submits, `fullWidth` for primary form CTAs. **Don't pass `color`** unless you need a non-primary variant — defaults pick up the theme's primary. For destructive actions, `color="red"`.
- **`Alert`** — `color="red" variant="light"` for errors, the primary color for info, `color="green" variant="light"` for success.

Form state lives in a view-local hook (`use-<name>-form.ts`) returning `{ form, handleSubmit, isLoading }`. UI binds to `form` props; submission logic stays in the hook. See `data-layer.md` § "Form-to-mutation pattern" and `conventions.md` § "Forms".

## Color scheme

Decide on a fixed color scheme up front (light only, dark only, or a true toggle) and stick to it. If the product is single-scheme, **don't** branch styling on `dark:` Tailwind variants or `[data-mantine-color-scheme='...']` selectors — define the tokens at `:root` instead. If a future design need requires a second visual mode (e.g. high-contrast), introduce it as a **named alternative scheme**, not as a generic "toggle."

## Anti-patterns

Warning signs that something's off — fix or refactor before moving on.

- **Hex literals or rgb/rgba in component code.** Use a token; if none fits, add one.
- **Inline `style={{}}` for static values.** Use Tailwind utilities.
- **`whileInView` for above-the-fold elements.** IntersectionObserver fires after paint — you'll see a flash of the `initial` state. Use `initial` + `animate`.
- **Raw `<input>` / `<button>` in forms.** Bypasses the themed Mantine layer.
---

## When in doubt

1. `grep` for the Tailwind classes you're considering. Match precedent over local cleverness.
2. If no precedent exists and you're inventing the pattern, prefer the more restrained option, and add a token rather than an inline value.
